# QAIMA 공개 정책 문서

## 0. 문서 목적

이 문서는 QAIMA의 아키텍처 경계, API 계약, 인증, 분석 기능, 오류 처리, 캐시, 데이터 적재, LLM 설명 및 분석 리포트 정책을 공개 가능한 범위에서 정리한다.

공개 문서에는 다음 정보를 포함하지 않는다.

- 운영 서버 주소 및 네트워크 정보
- 서버 접속 인증 정보와 키 경로
- 실제 서비스 도메인 및 관리자 계정 정보
- 환경변수 값과 Secret 설정
- 데이터베이스 직접 조작 SQL
- 서버 재시작·배포·복구 명령어
- 운영 중 발생한 일회성 장애와 임시 조치 기록
- 내부 로그 원문과 사용자 식별 정보

세부 배포 절차와 운영자용 진단 자료는 비공개 Runbook에서 별도로 관리한다.

## 1. 공통 아키텍처 및 계약 경계

QAIMA는 React 프론트엔드, Spring Boot 애플리케이션 서버, FastAPI 분석 서버, MySQL, Redis 및 외부 금융 데이터 제공처로 구성된다.

### 1.1 계층별 책임

| 계층 | 주요 책임 | 데이터 표기 |
|---|---|---|
| React Frontend | 사용자 입력, Public API 호출, 화면 표시, PDF 생성 | `camelCase` |
| Spring Public API | 인증, 권한, 크레딧, 데이터 조회·조립, 공통 응답 생성 | `camelCase` |
| Spring ↔ FastAPI | 내부 분석 요청과 응답 전달 | Wire 기준 `snake_case` |
| FastAPI | 정량 분석, 감성 분석, 클러스터링, LLM 설명 | `snake_case` |
| MySQL / Flyway | 영속 데이터와 스키마 이력 관리 | `snake_case` |
| Redis | 단기 캐시와 반복 계산 결과 재사용 | 도메인별 Key 규칙 |

### 1.2 기본 경계 규칙

- 프론트엔드는 Spring Public API만 호출한다.
- Spring은 인증, 권한, 크레딧, DB 및 외부 데이터 조회를 담당한다.
- FastAPI는 Public API 응답 형식을 생성하지 않고 분석 Payload만 반환한다.
- Spring은 FastAPI 응답을 Public DTO로 변환한 후 공통 응답 형식으로 감싼다.
- 외부 API 응답 구조를 프론트엔드에 그대로 노출하지 않는다.
- 분석 계산과 LLM 설명 생성을 분리한다.
- 기존 Public API는 명시적인 변경 승인 없이 호환성을 깨지 않는다.

### 1.3 공통 내부 요청 구조

Spring에서 FastAPI로 전달하는 분석 요청은 다음 논리 블록을 기준으로 한다.

```json
{
  "request_context": {},
  "subject": {},
  "input_data": {},
  "options": {}
}
```

| 블록 | 역할 |
|---|---|
| `request_context` | 기능 유형, 요청 식별자, 기준 시점, 투자 수준, 설명 생성 옵션 |
| `subject` | 종목 또는 포트폴리오 등 분석 대상 |
| `input_data` | 가격, 재무, 시장, 벤치마크, 외부 요인 등 원천 데이터 |
| `options` | 분석 기간, 계산 방식, 표시 모드, 모델 및 캐시 옵션 |

Spring DTO에서는 동일한 구조를 `camelCase`로 표현하고, 내부 API 경계에서 `snake_case`로 변환한다.

### 1.4 공통 설명 구조

Feature 1~3의 설명 결과는 가능한 한 동일한 Container를 사용한다.

```json
{
  "provider": "LLM|DETERMINISTIC",
  "model": "string|null",
  "text": "string|null",
  "sections": {},
  "overall": {
    "summary": "string",
    "bullets": [],
    "risks": [],
    "conclusion": "string|null"
  },
  "warnings": []
}
```

각 설명 섹션은 제목, 요약, 핵심 항목을 포함한다.

```json
{
  "title": "string",
  "summary": "string",
  "bullets": []
}
```

## 2. API 및 DTO 계약 정책

### 2.1 계약 계층

QAIMA의 계약은 다음 네 경계를 구분하여 관리한다.

| 계약 | 주 사용자 | 안정성 기준 |
|---|---|---|
| Spring Public API | 브라우저와 프론트엔드 | 가장 높은 호환성 유지 |
| Spring 내부 DTO | Spring과 분석 서버 | 명시적 변환과 테스트 필요 |
| FastAPI Pydantic Model | 분석 엔진 | 내부 계약으로 관리 |
| React Type / Mapper | UI 컴포넌트 | Public API와 동기화 |

### 2.2 Public API 원칙

- Public API는 버전이 포함된 공통 경로 아래에 구성한다.
- 성공, 부분 성공, 실패는 공통 응답 구조로 표현한다.
- Public 필드는 `camelCase`를 사용한다.
- 사용자 화면이 의존하는 필드는 문서화하고 안정적으로 유지한다.
- Optional 필드는 프론트엔드 Fallback 정책과 함께 추가한다.
- 디버그용 내부 필드는 사용자 화면에 직접 노출하지 않는다.

### 2.3 변경 분류

#### 호환 가능한 변경

- Optional 또는 Nullable 필드 추가
- 신규 Warning Code 추가
- 신규 설명 섹션 추가
- Diagnostics와 품질 메타데이터 추가
- 새로운 언어 또는 표시 옵션 추가

#### 호환성을 깨는 변경

- 기존 Public 필드 삭제
- 필드의 의미 또는 자료형 변경
- 기존 Enum 값 삭제 또는 의미 변경
- Route, Method, 필수 Parameter 변경
- 성공과 실패의 상태 의미 변경
- `camelCase`와 `snake_case` 경계 변경

호환성을 깨는 변경에는 버전 분리, 일정 기간의 이중 지원, Mapper 호환 또는 명시적인 Migration 계획이 필요하다.

### 2.4 계약 변경 검수

계약 변경 시 다음 항목을 확인한다.

```text
[ ] Public Route와 Method 변경 여부
[ ] Request/Response 필드 추가·삭제·의미 변경 여부
[ ] React Type과 Mapper 영향
[ ] Spring DTO와 FastAPI Model 간 Naming 일치
[ ] Error/Warning Code 추가 여부
[ ] 다국어 메시지 추가 여부
[ ] 기존 분석 리포트 Snapshot 호환성
[ ] 계약 Fixture와 예시 Payload 갱신
```

### 2.5 Golden JSON Fixture

중요 API는 정상, 부분 성공, 설명 실패, 데이터 부족 등 대표 사례의 JSON Fixture를 관리한다.

Fixture에는 실제 Token, 이메일, Secret, 운영 식별자를 포함하지 않는다. 사용자와 종목 데이터는 고정된 예시값 또는 비식별 값으로 작성한다.

권장 사례:

- Feature 1 정상 분석
- Feature 1 설명 생성 실패
- Feature 2 일부 데이터 누락
- Feature 2 Peer Cluster 누락
- Feature 3 정상 분석
- Feature 3 가격 또는 벤치마크 품질 저하
- 분석 리포트 상세 조회
- OAuth 추가정보 필요 상태

### 2.6 Deprecation

기존 필드 제거 전 다음 절차를 적용한다.

1. 신규 필드를 호환 방식으로 추가한다.
2. 서버와 프론트엔드가 신규 필드를 우선 사용한다.
3. 기존 필드를 Fallback으로 유지한다.
4. 문서에 Deprecated 사유와 제거 조건을 기록한다.
5. 검증 기간을 거친 후 제거한다.

## 3. 인증 및 사용자 정책

### 3.1 인증 상태

| 상태 | 설명 |
|---|---|
| Anonymous | 비로그인 사용자 |
| Authenticated | 인증 완료 사용자 |
| Email Unverified | 이메일 인증 미완료 |
| Profile Required | OAuth 가입 후 추가정보 필요 |
| Locked / Disabled | 접근이 제한된 계정 |

### 3.2 이메일 선 인증 회원가입

일반 회원가입은 이메일 인증을 완료한 뒤 계정을 생성하는 흐름을 사용한다.

```text
이메일 입력
→ 인증번호 발송
→ 인증번호 검증
→ 가입 정보 입력
→ 인증 상태 확인
→ 사용자 계정 생성
```

정책:

- 인증번호와 재설정 Token은 원문이 아닌 Hash 형태로 저장한다.
- 인증 정보에는 만료시간과 사용 여부를 둔다.
- 사용되었거나 만료된 인증 정보는 재사용할 수 없다.
- 이메일 또는 전화번호 중복을 확인한다.
- 비밀번호는 안전한 단방향 Hash 방식으로 저장한다.
- 인증 실패 사유를 과도하게 구체적으로 노출하지 않는다.

### 3.3 로그인과 Token

- Access Token은 짧은 수명으로 운영한다.
- Refresh Token은 HttpOnly Cookie로 관리한다.
- 서버에는 Refresh Token 원문 대신 Hash와 세션 상태를 저장한다.
- Token 갱신 시 기존 Refresh Token을 회전할 수 있다.
- 로그아웃 시 서버 세션을 폐기하고 Cookie를 만료시킨다.
- 프론트엔드는 인증 만료 시 중복 갱신 요청이 발생하지 않도록 처리한다.

### 3.4 OAuth

OAuth 로그인을 지원하며, Provider가 제공하지 않는 필수 프로필 정보는 별도 화면에서 입력받는다.

```text
OAuth 인증 성공
→ 내부 계정 또는 연결 계정 확인
→ 필수 프로필 확인
→ 추가정보 필요 시 Profile Required 상태
→ 추가정보 입력 완료
→ Active 상태 전환
```

OAuth 추가정보 입력은 오류가 아니라 정상적인 회원가입 단계로 취급한다.

### 3.5 사용자 프로필

사용자 프로필은 다음 항목을 포함할 수 있다.

- 이메일
- 이름
- 전화번호
- 생년월일
- 성별
- 국가
- 투자 수준
- 기본 위험회피계수
- 금융 용어 표시 설정
- 크레딧 잔액
- 계정 상태

민감한 개인정보는 화면과 로그에 필요한 범위에서만 노출한다.

### 3.6 투자 수준

| 수준 | 설명 정책 |
|---|---|
| Beginner | 쉬운 문장과 용어 풀이 중심 |
| Intermediate | 주요 지표와 관계 설명 |
| Advanced | 상충 신호와 위험 요인 설명 |
| Expert | 계량 결과와 모델 관점 설명 |

투자 수준은 설명 난이도만 조절하며, 계산 결과와 위험 등급을 변경하지 않는다.

## 4. Feature 분석 정책

### 4.1 공통 분석 흐름

```text
사용자 요청
→ 인증과 크레딧 확인
→ Spring 데이터 수집 및 정제
→ FastAPI 분석
→ Public DTO 변환
→ 분석 리포트 저장
→ 사용자 화면 반환
```

공통 원칙:

- 분석 전 크레딧을 차감할 수 있다.
- 분석 전체가 실패하면 정책에 따라 크레딧을 환불한다.
- 정량 분석 성공 후 설명만 실패하면 정량 결과를 유지한다.
- 리포트 저장 실패는 분석 전체 실패로 처리하지 않는다.
- 외부 데이터 일부 누락은 가능한 경우 Warning과 함께 부분 결과로 반환한다.

### 4.2 Feature 1 — 종목 심층 분석

Feature 1은 가격, 재무, 시장 스냅샷과 기술적 보조지표를 결합한다.

Spring의 책임:

- 종목 매핑
- 가격 시계열 조회 및 최신 데이터 보강
- 재무제표와 시장 스냅샷 조회
- 분석 요청 조립
- 리포트 저장
- Feature 3에서 재사용할 핵심 지표 캐시

FastAPI의 책임:

- OHLCV 요약
- 기술적 보조지표 계산
- 재무 타임라인 정리
- 시장 스냅샷 보정
- 선택적 자연어 설명 생성

주요 결과:

- 가격 흐름
- 재무 변화
- 시장 가치 및 수익성 지표
- 이동평균, 밴드, 모멘텀 지표
- 데이터 품질 Warning
- 사용자 수준에 맞춘 설명

### 4.3 Feature 2 — 외부 요인 분석

Feature 2는 다음 정보를 조합한다.

- 기준금리와 채권금리
- 환율
- 업종 및 산업 지수
- 공매도
- 투자자 수급
- 관련 뉴스와 뉴스 감성
- 유사 종목과 Peer Cluster

Feature 2는 개별 카드 조회와 종합 분석을 구분한다.

- 카드 조회는 화면 초기 로딩과 개별 정보 갱신에 사용한다.
- 종합 분석은 여러 외부 요인을 조합하여 자연어 설명을 생성한다.
- 일부 데이터가 없어도 가능한 데이터로 부분 성공을 반환한다.

#### Peer Cluster

Peer Cluster는 캐시를 우선 확인하고, 필요한 경우 산업 구성 종목과 가격·유동성·변동성 정보를 이용해 유사 종목을 계산한다.

주요 산출물:

- 기준 종목과 Peer의 상대 성과
- Peer 중심값과 범위
- 선정 Peer 목록
- 유동성 및 변동성 유사도
- 동시 상관과 선행·후행 관계
- 분석 Coverage와 품질 Warning

#### 뉴스 감성

뉴스 목록은 외부 뉴스 제공처와 DB/Redis 캐시를 조합해 구성한다.

- 뉴스 URL을 기준으로 중복을 최소화한다.
- 하나의 뉴스는 여러 종목과 연결될 수 있다.
- 기사 본문 추출 결과를 캐시한다.
- 로컬 감성 모델이 긍정·중립·부정 점수와 확률을 반환한다.
- 분석용 뉴스 수와 LLM에 전달하는 뉴스 수를 구분하여 관리할 수 있다.
- 설명에는 최근 뉴스 집합의 평균 감성이라는 의미를 명확히 표시한다.

### 4.4 Feature 3 — 포트폴리오 분석

Feature 3은 사용자의 보유 종목, 수량, 평균매입가, 현금 및 위험 성향을 기반으로 포트폴리오를 분석한다.

Spring의 책임:

- 종목 코드 정규화
- 가격 시계열 준비
- 벤치마크 시계열 준비
- 무위험수익률 결정
- Feature 1·2 오버레이 데이터 준비
- 크레딧 산정과 차감·환불
- 분석 리포트 저장

FastAPI의 책임:

- 수익률과 변동성 계산
- 공분산과 상관관계 계산
- 위험 기여도 계산
- CAPM 기반 기대수익률 분석
- Efficient Frontier
- 최대 샤프지수 포트폴리오
- 효용 최적 포트폴리오
- 설명 생성 또는 결정론적 Fallback

가격 데이터는 수정종가를 우선하며, 사용할 수 없는 경우 정의된 순서에 따라 다른 가격 데이터로 대체한다.

Fallback이 발생한 경우 다음 정보를 표시할 수 있다.

- 실제 사용한 가격 기준
- 데이터 제공처
- Fallback 여부
- 결측률과 표본 수
- 분석 품질 Warning

Feature 1과 Feature 2의 데이터는 핵심 최적화 결과를 대체하지 않으며, 보조적인 오버레이 신호로만 사용한다.

### 4.5 공통 차트와 시간 정책

- 일봉 데이터는 거래소의 거래일을 기준으로 해석한다.
- 거래소별 Timezone을 적용한다.
- 일봉 Timestamp는 일관된 Canonical 기준으로 저장하고 응답한다.
- 과거 형식의 데이터는 제한적인 호환 처리를 적용할 수 있다.
- 당일 미확정 일봉은 확정 데이터와 구분하여 처리한다.
- 외부 Provider가 반환한 시각은 거래소 기준일로 정규화한 후 저장한다.

## 5. 오류, 경고 및 프론트 메시지 정책

### 5.1 Error와 Warning

| 구분 | 의미 | 사용자 체감 |
|---|---|---|
| Error | 요청의 핵심 목적을 완료할 수 없음 | 오류 화면 또는 요청 실패 |
| Warning | 핵심 결과는 제공하지만 일부 데이터나 품질이 제한됨 | 결과와 안내 메시지 동시 표시 |

### 5.2 Error Code

Error Code는 `UPPER_SNAKE_CASE` 형식으로 관리한다.

주요 범주:

- 인증 및 권한
- 입력 검증
- 크레딧 부족
- 리소스 없음
- 외부 Provider 실패
- 분석 서버 실패
- 내부 처리 오류

프론트엔드는 서버 원문 메시지를 그대로 노출하지 않고 Error Code를 사용자 친화적인 다국어 문장으로 변환한다.

### 5.3 Warning Code

Warning은 분석 품질과 Fallback 상태를 설명한다.

대표 범주:

- 가격 데이터 Fallback
- 차트 데이터 부족
- 시장 스냅샷 일부 누락
- 벤치마크 부족
- 뉴스 감성 일부 실패
- Peer Cluster 누락
- LLM 설명 생략 또는 실패
- 분석 리포트 저장 실패
- 캐시 조회 실패 후 원본 데이터 사용

### 5.4 크레딧 정책

- 분석 실행 전 예상 비용을 확인한다.
- 분석 핵심 로직이 실패하면 사용한 크레딧을 환불한다.
- 설명 생성만 실패하거나 리포트 저장만 실패한 경우에는 정량 분석 성공 여부를 기준으로 처리한다.
- 크레딧 거래는 잔액과 별도의 Ledger에 기록한다.
- 중복 요청과 재시도로 이중 차감이 발생하지 않도록 식별자를 사용할 수 있다.

### 5.5 로그

로그에는 다음 정보를 포함할 수 있다.

- 요청 식별자
- 기능 구분
- 처리 단계
- 결과 상태
- Warning 또는 Error Code
- 외부 Provider 상태
- 처리 시간

로그에는 다음 정보를 기록하지 않는다.

- 비밀번호
- Access/Refresh Token 원문
- 인증번호와 재설정 Token
- API Secret
- 전체 개인정보
- 민감한 금융 입력 원문

## 6. Redis 및 캐시 정책

### 6.1 역할 구분

| 저장소 | 사용 목적 |
|---|---|
| Redis | 짧은 수명의 조회 캐시, 외부 API 결과, 계산 중간 결과 |
| DB Cache Table | 이력성과 기준일이 필요한 분석 결과 |
| MySQL Domain Table | 서비스의 기준 데이터와 영속 데이터 |

### 6.2 Key 규칙

Redis Key는 도메인과 식별자를 구분할 수 있는 Prefix를 사용한다.

```text
{domain}:{subdomain}:{identifier}:{version}
```

정책:

- 사용자 개인정보를 Key에 직접 포함하지 않는다.
- 날짜 기준 데이터는 기준일을 식별할 수 있어야 한다.
- Payload 구조가 변경되면 Version을 구분한다.
- 환경별 Namespace를 분리할 수 있다.

### 6.3 TTL

TTL은 데이터의 갱신 주기와 비용에 따라 다르게 설정한다.

- 실시간 또는 장중 데이터: 짧은 TTL
- 일 단위 시장 데이터: 거래일과 장 상태에 따른 TTL
- 뉴스 본문 및 감성: 비교적 긴 TTL
- Peer Cluster: 분석 기준과 파라미터에 따른 TTL
- Feature 오버레이: 최신성과 재계산 비용을 함께 고려

정확한 운영 TTL 값은 비공개 운영 설정에서 관리한다.

### 6.4 장애와 Fallback

- Redis Read 실패는 가능한 경우 Cache Miss로 취급한다.
- 원본 DB 또는 외부 Provider 조회를 시도한다.
- Redis Write 실패는 핵심 사용자 요청을 실패시키지 않는 것을 기본으로 한다.
- 직렬화 오류와 Payload Version 불일치는 캐시를 폐기하고 재생성한다.
- 캐시 장애가 데이터 정확성에 영향을 주는 경우 Warning을 제공한다.

### 6.5 캐시 대상

- 종목 랭킹
- 실시간 가격 및 시장 스냅샷
- 산업 지수
- Feature 2 뉴스와 감성
- Peer Cluster
- Feature 1 핵심 지표
- Feature 3 오버레이 신호
- 외부 Provider 조회 결과

## 7. ETL, Scheduler 및 시간축 정책

### 7.1 기본 원칙

ETL과 Scheduler는 다음 항목을 명시적으로 관리한다.

- 활성화 여부
- 실행 주기
- Timezone
- 대상 범위
- 호출 제한
- Retry와 Backoff
- 실행 Summary
- 중복 실행 방지

정확한 실행 시각과 운영 설정은 비공개 설정에서 관리한다.

### 7.2 데이터 적재 범위

- 종목 Master와 별칭
- 가격 OHLCV
- 재무제표
- 발행주식수
- 산업 및 산업 지수
- 종목별·시장별 투자자 수급
- 공매도
- 금리와 환율
- 뉴스와 뉴스 메타데이터
- 기관 보유 데이터

### 7.3 Idempotency

- 동일 기준일과 식별자의 데이터는 중복 적재하지 않는다.
- 재실행 시 기존 데이터와 신규 데이터를 안전하게 병합한다.
- 외부 Provider의 수정 데이터를 반영할 수 있는 갱신 정책을 둔다.
- 수동 보정 데이터와 자동 수집 데이터의 우선순위를 정의한다.

### 7.4 중복 실행 방지

- 단일 Scheduler 실행을 기본으로 한다.
- 다중 인스턴스에서는 분산 Lock을 사용한다.
- 장시간 작업은 실행 상태와 만료시간을 관리한다.
- 수동 실행과 자동 실행이 충돌하지 않도록 한다.

### 7.5 Retry

- 재시도 가능한 오류와 불가능한 오류를 구분한다.
- Rate Limit과 일시적인 네트워크 오류에는 Backoff를 적용한다.
- 인증·계약 오류는 무한 재시도하지 않는다.
- 종목 하나의 실패가 전체 Batch를 중단할지 여부를 작업별로 정의한다.

### 7.6 Batch Summary

Batch 작업은 다음 결과를 기록한다.

- 요청 또는 대상 건수
- 성공 건수
- 갱신 건수
- 건너뜀 건수
- 실패 건수
- 대표 실패 사유
- 시작·종료 시각
- 기준일

### 7.7 시간축

- 거래일 기준 데이터와 발표일 기준 데이터를 구분한다.
- 시장별 Timezone을 적용한다.
- 일봉은 거래소 거래일을 기준으로 정규화한다.
- 데이터의 `observedAt`, `publishedAt`, `tradingDate`, `asOf` 의미를 구분한다.
- 당일 미확정 데이터는 확정 데이터와 동일하게 취급하지 않는다.

## 8. LLM 및 Prompt 정책

### 8.1 역할 경계

LLM은 정량 분석 결과를 설명하는 보조 계층이다.

LLM이 담당하지 않는 항목:

- 수익률과 변동성 계산
- 공분산과 상관관계 계산
- CAPM 및 최적화 계산
- 위험 등급의 임의 변경
- 실제 데이터에 없는 수치 생성

### 8.2 출력 형식

- 가능한 경우 JSON 전용 출력 모드를 사용한다.
- 설명 결과는 구조화된 Schema에 맞춰 파싱한다.
- 잘못된 JSON은 정상 구조화 응답처럼 통과시키지 않는다.
- 파싱 실패 시 Warning과 결정론적 설명을 사용할 수 있다.
- Provider와 Model 정보는 리포트 재현성을 위해 기록할 수 있다.

### 8.3 Prompt Version

- Prompt에는 Version을 부여한다.
- 분석 리포트에 사용된 Prompt Version을 기록할 수 있다.
- Prompt 변경은 출력 구조와 사용자 체감 영향을 함께 검토한다.
- 동일 기능의 Prompt는 투자 수준별 표현만 달라지고 계산 의미는 유지해야 한다.

### 8.4 입력 최소화

LLM에는 설명에 필요한 요약 정보만 전달한다.

#### Feature 1

- 가격 흐름 요약
- 핵심 재무 변화
- 시장 스냅샷
- 기술적 지표 요약
- 데이터 품질 Warning

#### Feature 2

- 금리·환율·채권 요약
- 수급과 공매도
- 산업 지수
- Peer Cluster 요약
- 뉴스 감성 요약
- 최근 대표 뉴스 일부

#### Feature 3

- 현재 포트폴리오 요약
- 기대수익률과 변동성
- 위험 기여도
- 비교 포트폴리오
- Efficient Frontier 요약
- 오버레이 관측
- 사용자 위험 성향

### 8.5 투자 수준별 설명

- 초급: 짧고 쉬운 표현, 용어 풀이 중심
- 중급: 지표의 의미와 관계 설명
- 고급: 상충 신호와 데이터 한계 포함
- 전문가: 계량 모델, 추정 방식 및 진단값 중심

### 8.6 금지 표현

LLM 설명은 다음 내용을 생성하지 않는다.

- 특정 종목의 직접적인 매수 또는 매도 지시
- 수익 보장
- 확정적인 가격 전망
- 목표주가
- 근거 없는 수치
- 강제적인 추천 비중
- 직접적인 리밸런싱 명령
- 제공되지 않은 뉴스나 공시의 인용

허용되는 표현은 관찰, 가능성, 위험 요인, 데이터 한계 및 조건부 해석을 중심으로 한다.

### 8.7 실패 처리

- 설명 생성이 실패해도 정량 분석 결과를 유지한다.
- 결정론적 설명으로 대체할 수 있다.
- 설명 실패를 Warning으로 표시한다.
- 사용자가 설명 생성을 선택하지 않은 경우 생략 상태를 명확히 표시한다.

## 9. 분석 리포트 및 PDF 정책

### 9.1 리포트 저장

Feature 1~3 분석은 성공 후 리포트 Snapshot 저장을 시도할 수 있다.

리포트에는 다음 정보가 포함될 수 있다.

- 기능 유형
- 분석 대상
- 사용자명 Snapshot
- 투자 수준과 위험 성향
- 분석 기간과 가격 기준
- 데이터 기준일
- 분석 요청 Payload
- 결과 Snapshot
- Warning
- 사용한 분석 또는 설명 Model

리포트 저장 실패는 분석 성공을 무효화하지 않는다.

### 9.2 소유권

- 사용자는 본인의 리포트만 조회한다.
- 리포트 목록과 상세 조회 모두 소유권을 확인한다.
- 비소유 리포트의 존재 여부를 과도하게 노출하지 않는다.

### 9.3 보관

- 리포트 보존 기간은 서비스 정책으로 관리한다.
- 만료 리포트는 정기 작업 또는 조회 시점에 정리할 수 있다.
- 보존 기간 변경은 사용자 안내와 개인정보 정책을 함께 검토한다.
- 장기 보관이 필요한 리포트는 별도의 Export 정책을 적용할 수 있다.

### 9.4 PDF

- PDF 원본 바이너리를 서버에 필수 저장하지 않는다.
- 저장된 JSON Snapshot을 화면에 다시 렌더링하여 PDF를 생성할 수 있다.
- PDF 모드에서는 접힘, 스크롤, 애니메이션 등 화면 전용 요소를 인쇄 친화적으로 변환한다.
- PDF에는 분석 기준일, 생성일, 데이터 품질 Warning과 면책 문구를 포함할 수 있다.

## 10. 공개 운영 원칙

세부 운영 절차는 비공개 Runbook에서 관리하며, 공개 문서에는 다음 원칙만 포함한다.

### 10.1 배포

- Secret은 소스코드와 저장소에 포함하지 않는다.
- 환경별 설정을 분리한다.
- 데이터베이스 Schema는 Migration으로 관리한다.
- 배포 전 Build, Test, Migration 검증을 수행한다.
- 배포 후 핵심 기능 Smoke Test를 수행한다.
- Rollback 가능한 Artifact와 Migration 전략을 유지한다.

### 10.2 관측성

- 애플리케이션 상태와 분석 서버 상태를 점검할 수 있어야 한다.
- 인증, 외부 Provider, 분석 실패, Cache Fallback을 구분해 기록한다.
- 민감한 데이터와 Secret은 로그에서 마스킹한다.
- 운영 Metric과 Alert는 서비스 영향도를 기준으로 구성한다.

### 10.3 장애 대응

- 장애를 애플리케이션, 데이터베이스, 캐시, 외부 Provider, 분석 서버, 네트워크로 분류한다.
- 일시적 외부 장애에는 Fallback과 Retry를 적용한다.
- 데이터 정합성이 필요한 장애는 자동 복구보다 안전한 중단을 우선할 수 있다.
- 장애의 원인과 재발 방지 정책은 비공개 운영 기록에서 관리한다.
- 일회성 오류 해결 과정과 실제 명령어는 공개 문서에 포함하지 않는다.

### 10.4 데이터 보정

- 수동 데이터 보정은 승인된 절차를 따른다.
- 변경 전후 값과 기준일을 기록한다.
- 자동 적재 데이터와 수동 보정 데이터의 우선순위를 명확히 한다.
- 공개 저장소에는 실제 운영 데이터 수정 SQL을 포함하지 않는다.

## 면책

QAIMA는 금융 데이터를 수집·분석하고 사용자의 이해를 돕기 위한 정보 제공 시스템이다.

QAIMA는 특정 금융상품의 매수, 매도 또는 보유를 지시하지 않으며 투자 수익을 보장하지 않는다.

분석 결과는 사용된 데이터, 분석 기간, 모델, 외부 데이터 제공 상태와 사용자 입력에 따라 달라질 수 있다. 최종 투자 판단과 책임은 사용자에게 있다.
